Text field

A text field is where the user types one line of information — a name, an email, a search term, a URL. Give it a clear label so the user knows what to enter, helper text for the format you expect, and an error that explains how to fix it when something’s off. For longer answers like comments or descriptions, use a Text area instead.

Content GuidelinesRecommended

Do
  • Always give the field a visible label — not a placeholder, not just context. Screen readers and users alike need a name they can refer back to.
  • On desktop, prefer left labels in dense settings panels and admin tables; everywhere else, top labels are the safer default.
  • Switch to top labels on tablet and mobile — left labels squeeze the field too narrow once the viewport shrinks.
  • Use placeholder text for example formats only (“name@example.com”, “DD/MM/YYYY”). It disappears once the user types — never put critical info there.
  • Put format rules in helper text (“Letters and numbers only”, “Max 50 characters”) so they stay visible while the user is typing.
  • Show a character counter when there’s a real max — otherwise the user types blind and hits a wall.
  • Make every error tell the user how to fix it: “Enter a valid email” beats “Invalid input.”
  • Use prefix and suffix for fixed parts of the answer (“https://”, “@”, “.com”, “kg”) so the user doesn’t have to type them.
Don't
  • Don’t use placeholder text as the label — the moment the user starts typing, the prompt vanishes and they have to retype to remember what the field was for.
  • Don’t mix Error and Success on the same field at the same time. Pick the one the user needs to act on first.
  • Don’t use Read-only when you mean Disabled. Read-only says “this is the value, you can’t edit it here”; Disabled says “you can’t do anything with this field yet.”
  • Don’t stack a prefix icon and a prefix text together unless the design genuinely calls for both — the field starts to look crowded.
  • Don’t pad helper text into a paragraph. One short sentence — the user is mid-form, not reading docs.
  • Don’t hide the label and assume the surrounding UI explains the field. It rarely does, and screen readers always need it.

Label Position

Left labels are the default — they save vertical space in dense, wide forms (settings panels, admin tables) and align cleanly down a column. Switch to top labels for responsive/mobile layouts and narrow side panels, where an inline label would break down. Use none to hide the label when context already names the field (toolbar filters, table cells) — the label text is kept as the input’s aria-label for screen readers. Below 640px a left label automatically stacks on top.

When to Use

Reach for a text field whenever the user has to type a single line — their name, an email, a search term, a number. For longer freeform writing, use a Text area; for picking from a fixed list, a Dropdown.

  • Single-line text entry: For collecting short free-text input such as names, emails, URLs, or descriptions.
  • Form fields: As the primary building block for data collection forms across the application.
  • Search: Combined with a prefix search icon for search bars and filter inputs.
  • Filters: In data table toolbars and dashboards for filtering content inline.

Label Position Guidelines

Top labels are the safe default — they read top-to-bottom like the rest of the page and survive narrow screens. Use left labels only when vertical space is genuinely tight and the form is wide enough to give them room.

  • Desktop default: Always use Label Position = Left. This is the standard layout for desktop forms with sufficient horizontal space.
  • Responsive breakpoints: Auto-switch to Label Position = Top when the viewport width drops below the mobile breakpoint or when the form is inside a narrow container.
  • Narrow side panels: Use Label Position = Top when the text input appears inside drawers, side panels, or modal forms with limited width.

Prefix & Suffix Elements

A prefix or suffix replaces what would otherwise need its own line of helper text. Use them for fixed units (“https://”, “@”, “.com”, “kg”) — the part of the answer the user shouldn’t have to type.

RTL Support

In Arabic, Hebrew, and Persian, the whole field mirrors automatically — label, prefix/suffix, clear button, and helper text all swap sides. Set dir="rtl" on any ancestor and the component does the rest.

  • Layout mirrored: The entire input layout mirrors horizontally. Label moves to the right, input field aligns accordingly.
  • Prefix/suffix swap: Prefix elements appear on the right side and suffix elements on the left side in RTL mode.
  • Text alignment: Input text and placeholder text automatically right-align in RTL mode.
  • Helper row: Helper text starts from the right, counter moves to the left.

Instance Overrides

How to override a text field instance in Figma without detaching it — so your design stays in sync when the source component updates.

  1. Drag the Text Input component from the Assets panel onto your canvas.
  2. Select the instance and open the Properties panel on the right sidebar.
  3. Choose the desired Size (Small, Medium, or Large) from the variant axis dropdown.
  4. Set the State axis to match the interaction context (Default, Hover, Focus, Filled, Error, Success, Disabled, or Read Only).
  5. Toggle RTL to true if the form is rendered in a right-to-left language.
  6. Set Label Position to Left (desktop) or Top (responsive/mobile).
  7. Override the Label Text, Placeholder, and Helper Text string properties to match the field's purpose.
  8. Enable or disable Prefix Icon, Prefix Text, Suffix Text, Suffix Icon, Clear Button, and Counter as needed.
  9. Swap icon instances (Prefix Icon Instance, Suffix Icon Instance) to the appropriate icons from the icon library.

Accessibility

Most accessibility is already baked in — this section explains what your users get for free, and the few things you have to provide (a real label, helpful error text, ARIA on icon-only affixes).

Color ContrastWCAG AA

  • Input text (#1A1A2E) on white background maintains a contrast ratio of 15.1:1, exceeding WCAG AAA requirements.
  • Placeholder text (#8B95A9) on white background maintains a minimum contrast ratio of 3.5:1 for non-text UI elements.
  • Error state border (#C1181B) meets the 3:1 minimum for UI component contrast against white.
  • Helper text (#5F6C89) on white background maintains at least 4.6:1 contrast ratio for small text.
  • Label text uses the page's primary text color to ensure maximum readability.

Screen Reader

  • Always associate the <label> element with the input using the for attribute matching the input's id.
  • Use aria-describedby to link helper text and error messages to the input so screen readers announce them.
  • Use aria-required="true" on required fields to communicate obligation to assistive technologies.
  • Prefix and suffix text should be included via aria-label or visible label context so the format is clear (e.g., "Price in dollars").
  • The clear button should have an explicit aria-label="Clear input" for screen reader users.

Error Handling

  • Use aria-invalid="true" on the input element when the field is in the Error state.
  • Error messages must be linked via aria-describedby so the error is announced when the input receives focus.
  • Use aria-live="polite" on error message containers for real-time validation so errors are announced dynamically.
  • Do not rely solely on color (red border) to indicate errors. Always pair with a descriptive text message.

RTL Accessibility

  • Set dir="rtl" on the container or use CSS direction: rtl to ensure proper layout mirroring.
  • Ensure tab order remains logical in RTL mode (right-to-left reading order).
  • Verify that screen readers announce label and helper text in the correct reading direction.
  • All interactive elements (clear button, suffix icons) must remain reachable via keyboard in RTL layouts.

Disabled & Read Only

  • Disabled: Use the native HTML disabled attribute. The input is removed from tab order and cannot receive focus.
  • Read Only: Use the native HTML readonly attribute. The input remains focusable and its value can be copied, but it cannot be edited.
  • If a disabled field needs to explain why it is disabled, use aria-disabled="true" instead of the native disabled attribute so it remains focusable for tooltip access.

Label Position

  • Regardless of visual label position (Left or Top), the <label> must always be programmatically associated with its input.
  • When the label is visually hidden for design reasons, use aria-label or a visually-hidden label element to maintain screen reader support.
  • Label Position = Top may improve readability for screen magnifier users who zoom into narrow viewports.
