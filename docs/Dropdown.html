Dropdown Menu

A dropdown opens a short list under a trigger — the row actions for a table, the user menu under an avatar, the filter options under a chip. Pick it when the choices live tucked away until the user asks for them. For a long, searchable list of options inside a form, use a Dropdown Select; for filtering across many tags at once, use a Tab filter.

Do
  • Keep item labels short and scannable (1–4 words).
  • Use Multi Select when the user needs to confirm before applying.
  • Use With Sections when 2+ logical groupings exist with 3+ items each.
Don't
  • Use sentence-long descriptions as item labels.
  • Use Multi Select for single-pick scenarios (creates unnecessary friction).
  • Add a section with only 1 item — just place it in the flat list.

When and Where to Use

Reach for a dropdown when you have a short list of actions or options tied to one control — row menus, avatar menus, filter chips. For form selection from a known set, use a Dropdown Select; for navigation, use a Menu in the header.

When to use

  • Offer a contextual list of actions or options attached to a trigger element (button, icon button, field).
  • When there are too many options to display inline (typically 3 or more).
  • When the user needs to select one option and immediately apply it (Single Select).
  • When the user needs to select multiple options before committing (Multi Select).
  • When options fall into distinct logical groups (With Sections).

When NOT to use

  • For navigation — use a Nav Menu or Sidebar instead.
  • When there are only 2 options — use a Toggle or two Buttons.
  • When options need descriptions or rich content — use a Popover or Dialog.
  • As a form select input — use a Select Field component instead.

Alignment & Placement

The panel opens below the trigger by default and flips up when the viewport runs out of room. That predictability matters: the user’s eye should land on the first option without scanning around for the menu.

  • Below Trigger: The panel should appear directly below the trigger element, aligned to its left edge.
  • Left-Aligned: Default alignment is left-aligned with the trigger. In RTL mode, the panel aligns to the right.
  • Z-Index: Dropdown panels must appear above all page content. Use a z-index of at least 1000.
  • Viewport Boundary: If the panel would extend beyond the viewport, flip it above the trigger or shift it horizontally to remain visible.

Complete Do's and Don'ts

Specifics — how many items is too many, when to group, when destructive items warrant a confirmation. Each rule has a reason; read both before you bend one.

Do
  • Keep labels short: 1–4 words per item for fast scanning.
  • Close Single Select immediately on item selection.
  • Use Show Header=OFF when the trigger label already provides context.
  • Provide a "Clear All" path in Multi Select (Show Footer=ON).
  • Use With Sections when 2+ logical groupings exist with 3+ items each.
  • Use Multi Select when the user needs to confirm before applying.
Don't
  • No sentence labels: Don't use sentence-long descriptions as item labels.
  • No single-pick multi: Don't use Multi Select for single-pick scenarios.
  • No single-item sections: Don't add a section with only 1 item.
  • Don't leave Single Select open after a choice is made.
  • Don't always show header even when it duplicates the trigger label.
  • Don't force manual reset: Don't make users uncheck each item to clear.

RTL Support

  • When RTL=True, the entire panel is mirrored: header title moves right, dismiss icon moves left.
  • Item icons appear on the right side, labels align right.
  • Footer: "Apply" button moves to the left, "Clear All" to the right.
  • Set dir="rtl" on the containing wrapper — do not mirror manually with CSS transforms.
  • Use logical CSS properties (margin-inline-start, padding-inline-end) for proper bidirectional support.

Accessibility

Most accessibility is built in — this section explains what your users get for free, and the few things you have to provide: a clear trigger label, ARIA on icon-only triggers, and sensible keyboard semantics for the panel.

Keyboard Interaction

KeyAction
↓ / ↑Move focus between menu items.
Enter / SpaceActivate the focused item or toggle a checkbox.
EscapeClose the menu and return focus to the trigger element.
HomeMove focus to the first menu item.
EndMove focus to the last menu item.
TabMove focus to the next focusable element (footer buttons in Multi Select).

On open, focus moves to the first item in the list. On close (via Escape or selection in Single Select), focus returns to the trigger element that opened the menu.

ARIA Attributes & Screen Reader Guidance

  • role="menu" on the panel container to identify it as a menu to assistive technologies.
  • role="menuitem" for Single Select items; role="menuitemcheckbox" for Multi Select items.
  • aria-haspopup="menu" on the trigger element, combined with aria-expanded toggled on open/close.
  • aria-labelledby: Header text should be announced as the menu label via aria-labelledby.
  • Focus management: On open, focus moves to the first item. On close, focus returns to the trigger.
  • Multi Select Apply: The "Apply" button must be keyboard reachable and labeled aria-label="Apply selection" if icon-only.
  • RTL: Set dir="rtl" on the panel wrapper; rely on logical CSS properties.

Focus State Design

  • Focused menu items should display a visible focus ring (2px outline in the accent color, offset 2px).
  • The focus indicator must be visible in both light and dark themes.
  • Focus should not be trapped inside the menu — Tab key moves to footer buttons, then out of the panel.
