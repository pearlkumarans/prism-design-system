OTP Input

An OTP field is for typing in a short verification code — the 4 or 6 digits the user just got by SMS, email, or authenticator app. Each box reads one digit, auto-advances on type, and pastes a whole code in one go. Use it for login challenges, two-step verification, and email confirmations.

Content GuidelinesRecommended

Do
  • Set Length to match the actual code length sent to the user.
  • Display the Error state + helper text immediately on incorrect code.
  • Use autocomplete="one-time-code" for SMS autofill.
  • Show a clear helper text (e.g. "Code sent to +91 ••••••7890").
  • Clear all boxes and show Error state on wrong code.
Don't
  • Show a 6-box OTP for a 4-digit code — mismatched lengths confuse users.
  • Only reveal errors after the user submits the full form.
  • Disable paste — it frustrates users switching from SMS.
  • Leave the helper row empty — context reduces re-send rates.
  • Keep entered digits in Error state without clearing.

When and Where to Use

Reach for an OTP field anywhere the user has to type a short numeric code — SMS one-time passwords, email verification, two-step login, transaction confirmations. For passwords or other secrets, use a Text field with type="password" instead.

When to use

  • Verify identity via a numeric code sent by SMS, email, or authenticator app.
  • For 2FA (two-factor authentication) flows.
  • For PIN entry where each digit is individually confirmed.

When NOT to use

  • For passwords — use a password input field instead.
  • For codes longer than 6 digits — use a single text input with inputmode="numeric".
  • For alphanumeric codes — extend the component or use a standard text input.

Alignment & Placement

Consistent placement ensures the OTP Input is predictable and easy to locate.

  • Login / verification pages: Center the OTP Input horizontally on the page for a focused, hero-style placement.
  • Inline forms: Left-align the OTP Input with other form fields for visual consistency.
  • Mobile: Use Large size for comfortable touch targets. Center on screen for single-purpose verification flows.
  • RTL layouts: Set dir="rtl" on the wrapper and let the browser handle visual mirroring. Do not reorder DOM inputs.

Complete Do's and Don'ts

Specifics — how long the code should be, when to show a resend timer, what error text actually helps. Each rule has a reason; read both before you bend one.

Do
  • Match length to code: Set Length to match the actual code length sent to the user.
  • Immediate error feedback: Display the Error state + helper text immediately on incorrect code.
  • Enable SMS autofill: Use autocomplete="one-time-code" for SMS autofill.
  • Show context: Show a clear helper text (e.g. "Code sent to +91 ••••••7890").
  • Use Show Label=OFF only when the label is already provided by surrounding page content.
  • Clear on error: Clear all boxes and show Error state on wrong code — users should re-enter cleanly.
Don't
  • Mismatched length: Show a 6-box OTP for a 4-digit code — mismatched lengths confuse users.
  • Delayed errors: Only reveal errors after the user submits the full form.
  • Block paste: Disable paste — it frustrates users switching from SMS.
  • Empty helpers: Leave the helper row empty — context reduces re-send rates.
  • Hidden label without context: Hide the label without another visible indication of what the field expects.
  • Stale error digits: Keep entered digits in Error state without clearing.

RTL Support

  • Wrapper direction: Set dir="rtl" on the wrapper element. The browser handles visual mirroring of the flex layout.
  • Do not reorder DOM: Inputs remain in DOM order (1→4 or 1→6). The dir="rtl" attribute reverses the visual display.
  • Arabic labels: RTL variants use Arabic label text (رمز التحقق) and right-aligned helper text.
  • Keyboard navigation: Arrow keys follow visual direction — ArrowRight moves to the visually right box (which is the previous input in DOM order).
<div dir="rtl">
  <label>رمز التحقق</label>
  <div class="otp-fields">
    <!-- Inputs in DOM order (1→4), visually reversed by dir="rtl" -->
    <input ... aria-label="رقم 1 من 4" />
    ...
  </div>
</div>

Accessibility

Guidelines for ensuring OTP Input is accessible across assistive technologies and input methods.

Keyboard Interaction

ActionResult
Numeric key (0–9)Enters digit in focused box and auto-advances focus to next box.
Backspace on filled boxClears digit, stays on current box.
Backspace on empty boxMoves focus to previous box.
TabMoves focus to next box.
Shift+TabMoves focus to previous box.
Paste (full code)Distributes pasted digits across all boxes from the focused position.
ArrowLeft / ArrowRightMoves focus to adjacent box.

Auto-advance on input must not trap keyboard users; Tab must still work as expected to move focus out of the OTP group.

ARIA Attributes & Screen Reader Guidance

  • Group label: Wrap all digit inputs in a <fieldset> with a <legend> matching the label text.
  • Per-input label: Each <input> must have aria-label="Digit N of M" (e.g. "Digit 1 of 4").
  • Error announcement: When Error state activates, update an aria-live="assertive" region with the error message.
  • Helper text association: Associate the helper text with the group using aria-describedby on the <fieldset>.
  • Disabled: Disabled inputs must have the disabled attribute, not just visual styling.
  • Mobile autofill: autocomplete="one-time-code" enables OS-level SMS autofill without ARIA intervention.
  • Screen reader paste: Ensure paste events reflect the result back through value changes the screen reader can detect.
  • RTL: Set dir="rtl" on the wrapper; do not reorder DOM inputs.

Focus State Design

  • Visible focus indicator: The active box receives a 2px blue border (#006AFF) plus a blue shadow ring — this must not be overridden (WCAG 2.4.7).
  • Cursor indicator: A "|" cursor indicator appears inside the focused box to signal text input readiness.
  • Single active box: Only one box is focused at a time. Remaining boxes retain their current state styling.
