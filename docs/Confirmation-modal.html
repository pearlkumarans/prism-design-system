Confirmation Modal

A confirmation modal stops the user to make sure about something they can’t easily undo — deleting a project, sending an invoice, signing out across all devices. Keep it short: an icon for tone, a one-line question, one or two sentences of consequence, and two clear buttons (the destructive one named, never just “OK”). For form validation or non-blocking feedback, use an Inline message or Toast.

Content GuidelinesRecommended

Do
  • Lead the title with a verb naming the action: "Delete folder?", "Sign out everywhere?".
  • Use Destructive only for actions that cannot be undone, ever.
  • Match the primary button to the title's verb: title "Delete folder?" → button "Delete folder".
  • Keep the body to one or two short sentences.
  • Place Cancel on the left and the primary on the right.
  • Quantify the consequence ("14 records", "3 active sessions") — vague stakes feel less consequential.
Don't
  • Use generic titles like "Are you sure?" — they give the user nothing to read.
  • Use "OK" / "Yes" / "No" as button labels — they erase the meaning of the choice.
  • Pack the body with bulleted lists, FAQ-style explanations, or marketing language.
  • Reverse the button order or put the destructive action in the secondary slot.
  • Use Confirmation for forms or multi-step flows — reach for Modal / Standard instead.
  • Allow Destructive modals to dismiss on backdrop click (this is the default).

Usage

When to reach for a Confirmation Modal versus alternative feedback patterns.

When to use

  • The user is about to perform a discrete action that they should pause to confirm.
  • The action has a binary outcome (do / don't) and the context is short.
  • The decision fits in a 480 px dialog without scrolling.

When not to use

  • The action needs a form, multiple inputs, or a multi-step flow — use Modal / Standard or a side panel.
  • The user just needs acknowledgement, not a decision — use Toast or Inline alert.
  • The confirmation happens inline with a list row — use Inline Confirm instead.
  • You want to onboard or educate — use a coachmark or spotlight pattern.

Async confirm pattern

To keep the modal open while a handler runs:

modal.addEventListener('ds-confirmation-primary', async (e) => {
  e.preventDefault();           // prevent auto-close
  await api.delete(asset.id);
  modal.close();                // close after the work is done
});

Accessibility

Guidelines for ensuring the Confirmation Modal is accessible across assistive technologies and input methods.

Roles & ARIA

ConcernImplementation
Rolerole="alertdialog" with aria-modal="true" on the dialog.
Titlearia-labelledby pointing to the title element.
Bodyaria-describedby pointing to the body region.
Leading iconaria-hidden="true" — severity is conveyed by the title text and primary-button colour, not the icon alone.
Close buttonaria-label="Close".

Keyboard

KeyBehavior
EscDismiss (equivalent to Cancel). Suppress only when an inline confirmation chain explicitly disables it.
Tab / Shift+TabCycles focus inside the dialog only — focus is trapped while the modal is open.
EnterActivates the focused button. Does not auto-trigger the primary button.
Click on overlaySame as Cancel for Information / Warning. Disabled by default for Destructive to prevent accidental data loss.

Focus management

  • On open, focus moves to the secondary (safe) button — never the destructive primary.
  • Focus is trapped inside the dialog while open.
  • On close, focus returns to the originating trigger element (or returnFocusTo if set).
