Empty State

An empty state is what the user sees the first time they open a page that has nothing in it yet — no tickets, no devices enrolled, no reports created. Use it to explain what the feature is for in one short sentence, and give the user the one button that unblocks them (“Enrol a device,” “Create your first report”). An empty page is a chance to onboard, not a dead end.

Content GuidelinesRecommended

Do
  • Write a specific, feature-named title ("Start your first patch job").
  • Pair the empty state with at least one clear next action.
  • Use an illustration that matches the feature theme.
  • Keep description to ≤ 2 lines at the default size.
  • Use the primary-button style for the one expected next action.
  • Centre-align the block in its container.
Don't
  • Write generic titles ("No data", "Nothing here") — wastes the opportunity.
  • Show an empty state with no clear next step.
  • Use a generic mascot for unrelated features.
  • Write a paragraph of marketing copy in the description.
  • Stack multiple solid primary buttons — users cannot tell which to click.
  • Left-align the block in a wide container — it reads as an error.

When and Where to Use

Empty State is designed for zero-content surfaces — first-time lists, empty search results, gated views, and disabled features.

When to use

  • A list, table, or grid has no items yet for a first-time user ("no configurations yet").
  • A search / filter result is empty ("no matches for ‘xyz’").
  • A feature is available but not yet activated ("enable single sign-on to continue").
  • A permission-gated view has nothing to show for the current role.

When NOT to use

  • Loading — use a skeleton or spinner, not an empty state.
  • Error — use Inline Alert Message or a dedicated error state.
  • Success confirmation after an action — use a Toast.
  • First-run tutorials — use an onboarding flow, not an empty state.

Always pair an empty state with at least one path forward — create something, adjust filters, request access, or read more.

Message Tone

Write clear, specific copy that invites action. Avoid passive phrasing and marketing fluff.

ElementGuidance
TitleOne sentence, ≤ 50 characters. Action-oriented ("Start your first automation") or descriptive ("No configurations yet"). Avoid "There are no…".
Description1–2 sentences that explain what the feature does and why the user should act. End with a "Learn more" link when documentation exists.
Primary actionThe single most useful next step. Prefer a verb phrase — "Create configuration", "Invite teammate" — not "OK".
Secondary actionOptional lower-commitment alternative — "Learn more", "View docs", "Import". Omit when there’s nothing useful to offer.
Supported rowInclude only when platform compatibility materially affects the action (agent install, OS-targeted policy). Omit for generic empty states.

Complete Do’s and Don’ts

Guidelines for crafting effective empty states that drive user action.

Do
  • Write a specific title: "Start your first patch job" — feature-named, action-oriented.
  • Pair with an action: Every empty state must expose at least one clear next step.
  • Match illustration to feature: Use the domain-relevant spot illustration.
  • Keep description short: 1–2 lines max at default size.
  • Use one primary button: The one thing users should do next.
  • Centre the block: Keeps the page feeling intentional, not broken.
  • Hide Supported row when irrelevant: Only show OS icons for OS-specific actions.
  • Localise the Supported row: Translate OS names in Arabic/Hebrew/CJK layouts.
Don't
  • Generic titles: "No data", "Nothing here" — these waste the opportunity.
  • No action: Empty states without a next step leave users stuck.
  • Generic mascots: A cute character unrelated to the feature is noise.
  • Marketing paragraph: Avoid long, brochure-style descriptions.
  • Multiple primary buttons: Users cannot tell which is "the" action.
  • Left-align in wide container: Reads as an error, not an empty state.
  • Forced platform icons: Don’t show Windows/macOS/Linux on OS-agnostic features.
  • Unlocalised OS names: Don’t leave OS labels un-translated in RTL/CJK.

Accessibility

Guidelines for ensuring Empty State is accessible across assistive technologies and input methods.

Heading Hierarchy

  • Render the title as a real heading: Use <h2> or <h3> depending on page hierarchy so screen readers announce the landing.
  • Never skip levels: If the surrounding page uses an <h1>, the empty state title should be an <h2>.
  • Visual weight is not a heading: Don’t use a styled <div> — screen readers won’t find it in the outline.

ARIA Patterns

ConcernRequirement
LandmarkWrap the empty state in role="region" with aria-labelledby pointing to the title id. When it replaces the main content of a page, a <section> with aria-labelledby is sufficient.
IllustrationDecorative illustrations use aria-hidden="true" and alt="". Informative illustrations use role="img" with a descriptive aria-label.
Inline linkThe inline "Learn more" is a real <a> with a visible underline or colour and a non-colour hover affordance.
Button semanticsActions are <button> for in-app commands and <a> for navigation. Primary and secondary must have distinct visible styles — not rely on position alone.
Supported iconsEach OS icon has aria-label ("Windows", "macOS", "Linux"). If the row is purely decorative, set aria-hidden="true" on the icon cluster and keep only the label visible.
Live announcementIf the empty state appears dynamically (after a filter yields zero results), announce via an aria-live="polite" region so SR users hear "No matches found".

Focus Management

  • Tab order: title → inline description links → primary button → secondary button → supported-row icons (if interactive).
  • Visible focus ring: All focusable elements expose a 2 px focus ring that meets WCAG 2.4.7.
  • Do not autofocus: The empty state should not steal focus when it renders. Let the user keyboard-tab into it naturally.
  • Dynamic appearance: When the empty state replaces content after a user action (e.g. applying a filter), keep focus on the triggering control — don’t jump focus to the empty state.
  • RTL: Tab order follows DOM order; visual mirroring is handled by dir="rtl". The action cluster mirrors (primary visually on the right).

Screen Reader Guidance

  • Announce the landing: Because the title is a real heading within a region landmark, screen readers announce "region, [title], heading level 2" — clearly conveying "the list is empty, here’s what to do".
  • Describe the illustration only if informative: Most empty-state illustrations are decorative. Hide them with aria-hidden="true" to avoid redundant narration of "image" before the real content.
  • Keep button labels verbs: "Create configuration", "Invite teammate" — these are self-describing for SR users who encounter buttons out of visual context.
  • Localised Supported row: Translate OS names in Arabic/Hebrew/CJK layouts; never leave them un-translated.
  • Error vs empty distinction: If the surface is actually an error (network failure), use Inline Alert Message — not Empty State. SR users rely on the correct landmark/role.
