Button

A button is how the user pulls the trigger — save, send, delete, confirm. Pick a variant that matches the weight of the action: Primary for the one thing you want the user to do on this screen, Secondary for safe alternatives, Destructive for anything they can’t easily undo.

Content GuidelinesRecommended

Do
  • Use Primary for the one action you most want the user to take on this screen — Save, Continue, Send.
  • Use Destructive for anything the user can’t easily undo — Delete, Remove, Cancel subscription. Pair it with a confirmation when the cost is high.
  • Write labels as verbs, 1–3 words: “Save changes,” “Delete account,” “Send invite.” “Submit” alone tells the user nothing.
Don't
  • Don’t stack two Primary buttons next to each other — the user has to stop and pick, instead of acting.
  • Don’t use colour alone to flag danger. Pair the red Destructive variant with a verb that names the consequence: “Delete project.”

When and Where to Use

Reach for a button when the user is committing to something — submitting a form, confirming a choice, deleting a record, opening a dialog. For navigation between pages, use a Link instead.

When to use

  • The user commits to an action: Save, Submit, Delete, Publish.
  • Submitting a form or confirming what’s in a dialog.
  • Moving through a wizard or step-by-step flow (Next, Previous, Finish).
  • Flipping the interface into a new state — opening an editor, showing a preview, starting a process.

When NOT to use

  • For moving to another page or URL — that’s a Link, not a button. Right-clicking a button can’t open a new tab.
  • For showing and hiding content — use a Toggle, Accordion, or Tab instead. The user shouldn’t have to wonder whether a click commits anything.
  • For picking one of many options — reach for radios, a dropdown, or a tab filter, where all the choices are visible at once.

Alignment & Placement

Put primary actions where users already look for them. Consistent placement means they don’t scan the whole screen to find “Save.”

  • Forms: the Submit button sits at the bottom-left, aligned with the input column. Right-align it only inside filter panels where users expect “Apply” on the right.
  • Modals and dialogs: actions go bottom-right. The Primary button is always furthest right — that’s where the user’s thumb and eye land last.
  • Data tables: global actions like “Add user” live top-right above the toolbar, where they’re findable but don’t crowd the row controls.
  • Page headers: the page-level Primary belongs in the top-right of the banner. Users scan there first for the “do something here” button.

Complete Do's and Don'ts

Specifics — what to label buttons, how many primaries per screen, when to drop the icon, when to disable. Each rule has a reason; read both before you bend one.

Do
  • One Primary per view: the user’s eye is drawn to whichever button is loudest. Two Primaries side by side means neither leads.
  • Step down with Secondary or Outline: alternatives like “Cancel” or “Save as draft” should be lighter, not louder.
  • Order from least to most committal: Cancel on the left, Save on the right — that way the action with consequences is the one the user lands on last.
  • Show progress, don’t freeze: when a click kicks off work, switch the button to a loading spinner. A button that just goes grey looks broken.
  • Label icon-only buttons for screen readers: add aria-label to anything that’s just an icon — otherwise it’s announced as “button” with no clue what it does.
Don't
  • Don’t write essay labels: 1–3 words is the target. If you can’t fit the action in a verb phrase, the button shouldn’t be doing that work — use a link or a dialog.
  • Don’t wrap text: a button that breaks onto two lines reads as broken. If the label demands wrapping, rewrite it or pick a different control.
  • Don’t lean on colour alone: red doesn’t register for everyone. Back the Destructive variant with a clear verb — “Delete account,” not just “Confirm.”
  • Don’t hide a destructive action in a quiet button: if the click can’t be undone, it should look like it. Never wrap “Delete” in a low-key Secondary.

Implementation Idea: Form Submit

Bind loading to your submitting state so the user sees the click landed. The component renders a real <button> underneath, so native form behaviour (Enter to submit, validation, etc.) keeps working without extra wiring.

<!-- inside a <form> -->
<ds-button
  variant="primary"
  size="large"
  type="submit"
  prefix-icon="check"
  [loading] <-- toggle this attribute while submitting
>
  Save Changes
</ds-button>

RTL Support

  • When RTL = True, layout direction is mirrored — prefix icon moves to trailing, suffix to leading.
  • Text direction set to auto. All spacing and padding values are mirrored.
  • Icon positions swap accordingly to maintain visual hierarchy.

ARIA Attributes & Screen Reader Guidance

Whatever a sighted user reads on the button, a screen reader user has to hear. Icon-only buttons need a written label; loading states need a live announcement; destructive buttons should warn before they fire.

  • Use the native <button> element to inherit default accessibility behaviors. Avoid using <div> or <a> tags.
  • Icon-Only Buttons: Must explicitly define an aria-label describing the action to ensure screen reader support.
  • Disabled State: Use aria-disabled="true" instead of the native HTML disabled attribute if you need the button to remain focusable so tooltips can explain why it is disabled.
  • Loading State: Add aria-busy="true" and consider an aria-live region announcement.
  • State Toggling: For toggle buttons (like Pin vs Unpin), use aria-pressed="true" or aria-expanded="true" depending on the behavior.
  • Don't rely solely on color to communicate the button variant status — always pair with a clear label or descriptive icon.

Focus State Design

  • Focus ring: 2px solid using the variant's accent color (Primary: #006AFF).
  • Outer border radius: 12px, inner padding: 4px from focus ring.
  • Inner container retains the default state background.

WCAG 2.1 Level AA Requires: A contrast ratio of at least 4.5:1 for normal text (like most button labels) and 3.0:1 for large text and UI components (like icons and focus rings). All UEMS core buttons pass these standards.

Touch Target Size

On a phone or tablet, a button needs enough surface for a thumb to land cleanly. Aim for at least 44 × 44 px on touch — that’s the iOS / Material standard and what WCAG 2.5.5 recommends. Default to Large on mobile-first surfaces.
